# Происхождение профилей мер

Файлы скопированы без изменений из репозитория «Сканера»:
`azuresong-afk/scanner-way`, каталог `scanner/compliance/profiles/`, коммит `01e035a` (04.11.2026).

- Идентификаторы мер (`ИАФ.1`, `УПД.3`, мероприятия №117 `ВУ`, `КК`, …) совпадают со «Сканером» — по ним приходят автоматические результаты. Менять их нельзя.
- При загрузке в БД все записи получают `origin=scanner`, `verified=null` («требует сверки»): сопоставление «мера → техническая проверка» и применимость мер №21/№239 сделаны разработчиком «Сканера» и методистом не сверены.
- Обновление — через `GET /compliance/profiles` «Сканера» с показом разницы, а не ручной правкой этих файлов: «Справочники → Обновление из «Сканера»» (администратор). Сравнение ничего не меняет; применение выбранных мер — отдельное действие с ревизиями и записью в журнал. Настройка подключения — `GRC_SCANNER_*` в `.env` (сервисная учётная запись с ролью `auditor`).
- Загрузчик YAML при старте трогает профиль, только если файл изменился с прошлой загрузки, — поэтому перезапуск не откатывает обновление из API.
- `backend/app/integrations/scanner/fixtures/compliance_profiles.json` — ответ `GET /compliance/profiles` (форма `Profile.to_dict()` «Сканера»), собранный из этих же файлов; используется в тестах и при `GRC_SCANNER_MODE=fixture`.
