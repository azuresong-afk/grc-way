# Промт: продукт «Аттестация» — помощник по соответствию ФСТЭК №117 / №21 / №239

> Вставьте этот текст целиком первым сообщением в новый проект. Вместе с ним загрузите в проект папку `attachments/compliance-profiles/` (YAML-профили мер из «Сканера»). Рабочее название «Аттестация» (id `grc`) можно поменять.

## Кто ты и что делаем

Ты — ведущий разработчик продукта «Аттестация». Это рабочее место специалиста по защите информации и методиста в компании, которая выполняет **авторизованный договорной аудит и аттестацию** информационных систем заказчиков по требованиям ФСТЭК России. Продукт ведёт объект от классификации до комплекта документов:

1. описание информационной системы и определение класса / уровня защищённости / категории;
2. базовый набор мер по классу → адаптация (исключение с обоснованием, компенсирующие меры, дополнение);
3. оценка реализации каждой меры: **автоматически** по результатам «Сканера» (технические проверки на хостах) и **вручную** (организационные меры: документ, интервью, осмотр, сертификат СЗИ);
4. модель угроз по Методике ФСТЭК 2021 с использованием банка угроз БДУ;
5. комплект документов для аттестации (DOCX/PDF) и план устранения несоответствий, который уходит в продукт «Устранение».

Продукт — третий в семействе: «Сканер» (есть), «Устранение» (делается параллельно), «Аттестация» (ты). Все три встанут вкладками в общий кабинет «Платформа»: тот же внешний вид, тот же стек и «Контракт платформы v1» (ниже) обязательны.

## Нормативная база и честность данных

Покрываем: приказ ФСТЭК №117 от 11.04.2025 (ГИС и иные ИС госорганов, ГУП, госучреждений; действует с 01.03.2026, заменил приказ №17) с методическим документом ФСТЭК от 12.04.2026 «Состав и содержание мероприятий и мер…»; приказ ФСТЭК №21 от 18.02.2013 (ПДн) с ПП РФ №1119 от 01.11.2012 (уровни защищённости); приказ ФСТЭК №239 от 25.12.2017 (значимые объекты КИИ) с ПП РФ №127 от 08.02.2018 (категорирование) и формой сведений по приказу ФСТЭК №236; Методика оценки угроз безопасности информации (ФСТЭК, 05.02.2021) и банк данных угроз БДУ (УБИ); порядок аттестации по приказу ФСТЭК №77 от 29.04.2021; ГОСТ Р 51583-2014. Профили CIS — как дополнительные, без документов аттестации.

Правила:
- **Не выдумывай нормативный текст.** Таблицы классификации (класс ГИС, УЗ ПДн, показатели значимости КИИ), составы мер и формулировки документов хранятся в редактируемых справочниках (YAML в репозитории + правка в интерфейсе) с указанием источника: документ, пункт, приложение. Начальное наполнение делай по официальным текстам, которые владелец загрузит в проект; где текста нет — заглушка с пометкой.
- У каждой записи справочника флаг **«Сверено методистом»** (кто и когда). Пока не сверено — в интерфейсе и в документах значок «требует сверки», а в документах водяной знак «Проект».
- Продукт помогает специалисту, а не заменяет его: итоговый класс, адаптация и заключение утверждаются человеком с правом `approve`, всё фиксируется в журнале.

## Справочник мер: совместимость со «Сканером»

В «Сканере» уже есть профили соответствия: `fstec-117` (классы К1–К3), `fstec-21` (УЗ1–УЗ4), `fstec-239` (категории 1–3), `cis-controls-v8`, `cis-benchmark`. Файлы во вложении `attachments/compliance-profiles/` (`fstec-*.yaml`, `cis-*.yaml`, `checks.yaml` — каталог технических проверок с рекомендациями). Формат профиля: `id, title, short, document, url, level_label, levels[], default_level, groups[{code, title, controls[{id, title, levels[], checks[]}]}]`; мера без `checks` — организационная («проверяется вручную»).

**Идентификаторы мер (`ИАФ.1`, `УПД.3`, мероприятия №117 `ВУ`, `КК`, …) должны совпадать с «Сканером»** — по ним приходят автоматические результаты. Импортируй эти YAML как начальный справочник и умей обновлять его из `GET /compliance/profiles` «Сканера» (с показом разницы перед применением). Сопоставление «мера → техническая проверка» и применимость мер №21/№239 в «Сканере» сделаны разработчиком и **не сверены методистом** — помечай их соответственно.

## Предметная модель

- **Заказчик** (организация: реквизиты, ответственные лица) и **проект** (договор).
- **Объект** — информационная система (или АС / ЗО КИИ) внутри проекта: тип (ГИС / ИСПДн / ЗО КИИ / иная), назначение, состав (сегменты, хосты — из активов «Сканера» по группам), границы, взаимодействие с другими системами, подключение к интернету, ответственные.
- **Классификация** — мастер: для ГИС — класс К1–К3, для ИСПДн — УЗ1–УЗ4 (категории ПДн, число субъектов, сотрудники/не сотрудники, тип актуальных угроз 1–3), для КИИ — категория 1–3 по показателям значимости. Итог с обоснованием → документ «Акт классификации / определения уровня защищённости / сведения о категорировании».
- **Набор мер объекта** = базовый по классу + адаптация. Для каждой меры: статус `Реализована / Частично / Не реализована / Не применима`, способ оценки (авто / вручную / смешанный), доказательства, ответственный, комментарий, кто подтвердил.
- **Доказательства:** автоматические — результат прогона «Сканера» по профилю (номер и дата прогона, процент, хосты с нарушениями, рекомендации), с фиксацией *снимка* на дату оценки; ручные — файл (документ, скриншот, конфигурация), запись интервью, протокол осмотра. Файлы хранятся в БД или в томе с проверкой типа и размера, без исполнения.
- **СЗИ** — реестр средств защиты на объекте: наименование, номер сертификата ФСТЭК, срок действия, класс/уровень доверия, какие меры закрывает; предупреждение об истекающих сертификатах; импорт реестра сертифицированных СЗИ из CSV/XLSX, который загружает пользователь.
- **Модель угроз** (Методика 2021): виды негативных последствий (У1 — физическим лицам, У2 — юрлицам/ИП, У3 — государству), объекты воздействия, источники угроз и категории нарушителей с уровнями возможностей Н1–Н4, интерфейсы и способы реализации, сценарии (тактики и техники из приложения к Методике), перечень угроз из БДУ (импорт `thrlist.xlsx` с bdu.fstec.ru, загружает пользователь) → актуальные угрозы с обоснованием. Найденные «Сканером» уязвимости с идентификаторами БДУ привязываются к угрозам как подтверждение актуальности.
- **Несоответствия** — меры «Не реализована / Частично» → план устранения; технические пункты одной кнопкой уходят заявками в «Устранение» (событие или API), их статус возвращается обратно.
- **Документы** — версии, статус (`черновик → на согласовании → утверждён`), кто утвердил, сравнение версий.

## Комплект документов (генерация DOCX, затем PDF)

Шаблоны — DOCX с полями (docxtpl/Jinja), лежат в репозитории, пользователь может загрузить свой фирменный шаблон. Типографика по умолчанию — Inter / PT Astra Serif (на выбор), как в отчётах «Сканера»: аккуратные таблицы, обложка, оглавление. В комплект:
1. Акт классификации ГИС / акт определения уровня защищённости ПДн / сведения о категорировании объекта КИИ.
2. Модель угроз безопасности информации (структура по Методике 2021).
3. Частное техническое задание на систему защиты информации.
4. Технический паспорт объекта (состав, конфигурация, СЗИ — из активов и реестра СЗИ).
5. Организационно-распорядительные документы: политика, положение о разграничении доступа, инструкции администратора безопасности и пользователя, порядки управления конфигурацией, уязвимостями и обновлениями, реагирования на инциденты, резервного копирования (для №117 — по мероприятиям МРП).
6. Программа и методики аттестационных испытаний.
7. Протоколы испытаний по группам мер с автоматическими доказательствами (прогон, дата, процент, нарушения по хостам) и ручными.
8. Заключение по результатам испытаний и проект аттестата соответствия.
9. План мероприятий по устранению несоответствий (сроки — необязательное поле, по умолчанию не выводятся).

Каждый документ показывает, из каких данных он собран, и пустые поля, которые нужно заполнить.

## Роли

- **Методист** (`methodologist`): ведёт объекты, классификацию, адаптацию, модель угроз, документы.
- **Эксперт / испытатель** (`assessor`): оценивает меры, прикладывает доказательства, ведёт протоколы.
- **Утверждающий** (право `approve`): утверждает класс, адаптацию, модель угроз, заключение; не может утверждать собственную работу.
- **Наблюдатель** (`viewer`): представитель заказчика — просмотр и выгрузка утверждённых документов.
- **Администратор** (`admin`): пользователи, справочники (с флагом сверки), интеграции, журнал; рабочих операций не выполняет.

## Экраны

1. **Сводка** — объекты проекта: класс, % реализации мер (авто / вручную / всего), готовность комплекта документов, истекающие сертификаты СЗИ, несоответствия по уровню.
2. **Объекты** — список и карточка объекта (вкладки: Описание, Классификация, Меры, Модель угроз, СЗИ, Документы, История).
3. **Меры** — таблица по группам (`ИАФ`, `УПД`, …) со статусом, способом оценки, доказательствами; фильтры «не реализовано», «требует ручной оценки», «требует сверки»; шторка меры: требование, проверки «Сканера» и их результат по хостам, ручные доказательства, рекомендации; кнопки «Подтвердить», «Отправить в Устранение».
4. **Модель угроз** — мастер по шагам Методики с прогрессом и итоговым перечнем актуальных угроз.
5. **Документы** — комплект с готовностью каждого, генерация, версии, согласование.
6. **Справочники** — нормативные документы, профили мер, таблицы классификации, угрозы БДУ, реестр СЗИ; у каждой записи источник и флаг «Сверено методистом».
7. **Администрирование:** Пользователи и роли, Источники (подключение к «Сканеру» и «Устранению»), Журнал аудита.

## Интеграции

- «Сканер» (только чтение, роль `auditor`): `GET /compliance/profiles`, `GET /engagements/{id}/compliance-profiles`, `GET /runs/{id}/compliance?profile=&level=&group_id=`, активы и группы, находки с БДУ. Выбор прогона для оценки — вручную или «последний завершённый»; результат сохраняется снимком.
- «Устранение»: создание заявок по несоответствиям, получение статусов (`vm.ticket.status_changed`, `vm.remediation.verified`) → обновление доказательства меры.
- Режим платформы — события `grc.assessment.updated`, ссылки «Открыть в Сканере / Устранении».

## Этапы (предложи свою разбивку в `docs/roadmap.md`, затем реализуй по задачам)

- **Этап 1 (MVP):** проекты, объекты, справочник мер из YAML «Сканера», классификация (мастер на редактируемых таблицах), набор мер с адаптацией, импорт автоматических результатов из «Сканера», ручная оценка с доказательствами, сводка, журнал аудита, Docker.
- **Этап 2:** модель угроз по Методике 2021 с импортом угроз БДУ и привязкой уязвимостей; реестр СЗИ.
- **Этап 3:** генерация комплекта документов (DOCX/PDF), версии и согласование; связь с «Устранением»; режим `AUTH_MODE=platform` и манифест.

**Критерии приёмки MVP:** демо-объект «ГИС, класс К2» с 10 хостами и фикстурой ответа `GET /runs/{id}/compliance` → автоматические меры получают статусы с доказательствами, организационные ждут ручной оценки; адаптация с обоснованием отражается в проценте; повторный импорт другого прогона создаёт новый снимок, не затирая старый; всё, что не сверено методистом, видно как «требует сверки»; стиль неотличим от «Сканера» в обеих темах; тесты зелёные.

Начни с `docs/roadmap.md` (архитектура, модель данных, API, экраны, этапы с задачами и критериями) и короткого списка вопросов, которые реально меняют решение (например: какие официальные тексты владелец загрузит первыми, нужен ли свой шаблон документов); по остальному выбирай сам и отмечай выбор в документе.

## Единый стиль оформления (обязательно, совпадает со «Сканером»)

Новый интерфейс должен выглядеть как продолжение существующего продукта «Сканер»: пользователь переключается между продуктами и не замечает смены стиля. Не используй UI-библиотеки (MUI, Ant, Chakra, Tailwind, shadcn и т. п.) и не придумывай свою палитру: только токены ниже и описанные компоненты.

**Стек фронтенда:** React 18 + TypeScript (strict) + Vite 5, react-router-dom 6, иконки lucide-react (обводка, размер 18 в меню и 15 в кнопках), свой CSS на CSS-переменных (один файл `styles.css` или набор файлов с теми же классами), графики — свой SVG без чарт-библиотек. Тесты vitest + @testing-library/react, ESLint 9 (typescript-eslint, react-hooks). Шрифт Inter, моноширинный JetBrains Mono; шрифты подключать локально (пакеты `@fontsource/inter`, `@fontsource/jetbrains-mono`), без Google Fonts: у заказчиков бывают закрытые контуры, а CSP разрешает шрифты только с `'self'`.

**Язык интерфейса — русский**, ровный деловой тон, без англицизмов там, где есть русское слово («Сводка», «Активы», «Отчёты», «Журнал аудита»). Даты `04.11.2026 16:54`, числа с неразрывным пробелом-разделителем тысяч (`toLocaleString("ru-RU")`), проценты без дробной части, если она не важна.

## Что уже есть: продукт «Сканер» (ты его не видишь, вот всё нужное)

«Сканер» — собственный сетевой сканер уязвимостей уровня Сканер-ВС / XSpider для **авторизованного договорного пентеста**: работает только по целям из allowlist проекта, с ограничением скорости и неизменяемым журналом аудита. Репозиторий отдельный, в этом проекте его нет; интеграция — только через его REST API и описанный ниже контракт.

**Стек «Сканера»** (держись того же): Python 3.12, FastAPI, SQLAlchemy 2 + Alembic (миграции под PostgreSQL, нумерация `0001_…`, тест-страж непрерывности цепочки миграций в CI), PostgreSQL 16, pytest; Docker Compose: сервисы `app` (API :8000), `web` (nginx-unprivileged :8080, отдаёт SPA и проксирует `/api/*` → API с отрезанием префикса, один origin, без CORS), `db`. Секреты в `.env`, порты хоста настраиваются (`SCANNER_WEB_PORT=18080`, `SCANNER_API_PORT=18000`, `SCANNER_DB_PORT=15432`). Строгий CSP в nginx (`default-src 'self'`, `frame-ancestors 'none'`).

**Предметная модель «Сканера»:**
- *Проект* (в API — `engagement`): `{id, name, client, contract_ref, created_by, created_at}`; у проекта allowlist адресов/подсетей/диапазонов (сканировать можно только их).
- *Прогон* (`run`): `{id, engagement_id, name, modules[], targets[], status, started_at, finished_at, progress, warnings[], options}`; статусы `pending/running/done/partial («Частично»)/failed/stopped/interrupted («Прерван»)`; завершённые — все, кроме `pending/running`. Модули: `discovery` (nmap), `vuln` (Nuclei), `auth_inventory` (пакеты по SSH → CVE/БДУ, бюллетени дистрибутивов, ядро), `win_inventory` (WinRM), `config_audit` (OpenSCAP/Lynis по SSH), `cred_audit` (аудит слабых паролей по согласованию).
- *Находка* (`finding`): `{id, dedup_key, module, host, port, finding_type (vuln|config|cred|info…), title, severity (critical|high|medium|low|info), vuln_id, cve_ids[], bdu_ids[], cvss, evidence, status (new|open|regression|fixed), detected_at, software, software_version, priority{rank,score,label,label_ru,reasons[],factors}, confidence (high|medium|low), source, false_positive}`. **`dedup_key` = sha256(host|port|vuln_id|module) — стабилен между прогонами**, по нему сравниваются прогоны и по нему же надо связывать свои записи с находками.
- *Действие исправления* (`GET /runs/{id}/fixes`, раздел «Что исправить»): находки сгруппированы в действия `{key, kind (package|package_nofix|package_upgrade|kernel|software|config|cred|vuln|other), title, os, os_family, manager (apt|yum|dnf|zypper|apk…), packages[], fixed_version, steps[], commands[] (готовые команды под ОС, напр. `apt-get install --only-upgrade openssh-server`), verify[], reboot (bool), severity, priority, cves[], bdu_ids[], advisories[], references[], hosts[{host, installed, note, ports[], findings[{id,label,severity}]}], host_count, finding_count}`. `key` — хэш (вид, ОС+релиз, пакет), стабилен, пока не меняется состав пакетов.
- *Покрытие прогона* (`GET /runs/{id}/coverage`): для каждого хоста и модуля статус `completed | unreachable | timeout | no_credentials | not_applicable | skipped | error`. **Отсутствие находки считается исправлением только если хост+модуль в этом прогоне `completed`**, иначе результат «не проверено».
- *Активы*: `{id, engagement_id, address, hostname, owner, criticality (low|medium|high|critical), notes, tags[], groups[], os_guess, os_family, finding_counts, last_seen_at, source (manual|discovered)}`, группы активов.
- *Соответствие* (R5): профили `fstec-117` (ГИС, классы К1–К3), `fstec-21` (ПДн, УЗ1–УЗ4), `fstec-239` (КИИ, категории 1–3), `cis-controls-v8`, `cis-benchmark`. Профиль — YAML: группы мер (`ИАФ`, `УПД`, `ОПС`, `ЗНИ`, `РСБ`, `АВЗ`, `СОВ`, `АНЗ`, `ОЦЛ`, `ОДТ`, `ЗСВ`, `ЗТС`, `ЗИС`, `ИНЦ`, `УКФ`; у №117 свой состав — 19 мероприятий МРП `ВУ, КК, КУ, КО, …, ПК` и группы `ИАФ, УПД, РСБ, ЗСВ, ЗКО, ЗЭП, ЗВТ, ЗПИ, ЗКУ, ЗМУ, ЗИВ, ЗБД, АВЗ, СОВ, МСЭ, ЗОО, ЗКС`) → мера `{id, title, levels[], checks[]}`; мера без `checks` — организационная, «проверяется вручную», в процент не входит. Результат прогона по профилю: `percent`, `counts{passed,failed,na,manual}`, `controls[{id,title,group,status,hosts{...},failed_hosts[{host,checks[{id,failures[]}]}],recommendations[]}]`, `manual[]`, разбивка по хостам и группам. Сопоставление «мера → техническая проверка» сделано разработчиком и ещё не сверено методистом.
- *Справочники*: БДУ ФСТЭК (≈98 600 записей из vullist.xlsx), NVD, EPSS, CISA KEV, бюллетени Debian/Ubuntu/Astra/РЕД ОС/ALT/RHEL (OVAL), MSRC.
- *Роли*: `admin` (пользователи, проекты, allowlist, аудит; **без запуска сканов** — разделение обязанностей), `operator` (запуск/остановка, просмотр, разметка ложных срабатываний), `auditor` (просмотр, выгрузка, журнал), отдельные права-надбавки `cred_audit`, `host_credentials`. Права проверяются на каждый запрос из БД (отзыв роли действует сразу).
- *Журнал аудита*: append-only (триггер в PostgreSQL запрещает UPDATE/DELETE), кто/что/когда/результат, выгрузка.

**API «Сканера», которое понадобится** (Bearer-токен; через nginx — с префиксом `/api`):
- `POST /auth/token` `{username, password}` → `{access_token, token_type, expires_in}`; `GET /me` → `{id, username, display_name, roles[], permissions[]}`.
- `GET /engagements`, `GET /engagements/{id}`, `GET /engagements/{id}/allowlist`.
- `GET /engagements/{id}/runs?status=&limit=&offset=` (всего — заголовок `X-Total-Count`), `GET /runs/{id}`, `GET /runs/{id}/events` (лента событий прогона), `GET /engagements/{id}/trend`.
- `GET /runs/{id}/findings?severity=&status=&module=&host=&q=&sort=&order=&limit=&offset=`, `GET /runs/{id}/findings/summary`, `GET /findings/{id}`.
- `GET /runs/{id}/fixes`, `GET /runs/{id}/coverage`, `GET /runs/{id}/packages`, `GET /runs/{id}/services`.
- `GET /engagements/{id}/hosts`, `GET /engagements/{id}/hosts/{host}/latest`, `GET /engagements/{id}/assets`, `GET /engagements/{id}/asset-groups`.
- `GET /compliance/profiles`, `GET /engagements/{id}/compliance-profiles`, `GET /runs/{id}/compliance?profile=fstec-117&level=К2&group_id=`.
- `POST /engagements/{id}/runs` `{targets[], modules[], rate_profile (gentle|normal|fast), vuln_engine (nuclei|credentialed|both), credential_ids[], name, profile}` → прогон + `accepted_targets`, `denied_targets[]` (цели вне allowlist отклоняются сервером). Нужна роль `operator` (+`host_credentials` для модулей по учётной записи).
- `GET /runs/{id}/report?format=html|pdf|docx|json&variant=full|brief`.

Для интеграции заводи в «Сканере» **сервисную учётную запись** с минимальными ролями: только чтение — `auditor`; повторная проверка — `operator` (+`host_credentials`). Учётные данные — в `.env`/секретах, не в БД открытым текстом. Пока платформы нет, ходи в API «Сканера» по его собственному токену; после появления платформы — по токену платформы (см. «Контракт платформы»). Всё обращение к «Сканеру» держи в одном адаптере (`integrations/scanner/`) с моками в тестах, чтобы продукт собирался и тестировался без живого «Сканера».

## Контракт платформы v1 (одинаковый текст во всех трёх проектах)

Три продукта — «Сканер» (есть), «Устранение» (управление уязвимостями и обновлениями) и «Аттестация» (помощник по ФСТЭК №117/21/239) — собираются в один кабинет «Платформа», где продукты открываются как вкладки. Продукты разрабатываются параллельно в разных проектах, поэтому все следуют одному контракту. Каждый продукт обязан **работать и отдельно** (свой вход, свой docker compose), **и внутри платформы** (режим включается переменной окружения), без форков кода.

**1. Адреса (один origin, без CORS).** Шлюз платформы (nginx) отдаёт:
- `/` — оболочка платформы, `/scanner/`, `/vm/`, `/grc/` — SPA продуктов (Vite `base` настраивается переменной сборки `VITE_BASE`, по умолчанию `/`);
- `/api/platform/`, `/api/scanner/`, `/api/vm/`, `/api/grc/` — API (префикс отрезается шлюзом; API продукта о префиксе не знает). Фронтенд продукта берёт префикс API из `VITE_API_BASE` (по умолчанию `/api`).
- Идентификаторы продуктов: `scanner`, `vm`, `grc`. Порты для отдельного запуска: «Сканер» web 18080 / api 18000 / db 15432; «Устранение» 18081 / 18001 / 15433; «Аттестация» 18082 / 18002 / 15434; «Платформа» шлюз 18090 / api 18010 / db 15440.

**2. Вход и единая сессия (SSO).** Переменная `AUTH_MODE=local|platform`.
- `local` — свой вход по логину/паролю (scrypt, токен HMAC или JWT), как в «Сканере».
- `platform` — продукт не хранит пароли. Платформа выдаёт access-токен JWT, подпись **EdDSA (Ed25519)**, TTL 15 мин, обновление по httpOnly-cookie `platform_refresh` (Path=/api/platform/auth, SameSite=Strict, Secure) через `POST /api/platform/auth/refresh`. Открытые ключи — `GET /api/platform/.well-known/jwks.json` (кэш 10 мин, поддержка ротации по `kid`). Утверждения токена:
  ```json
  {"iss":"platform","sub":"<uuid пользователя>","aud":["scanner","vm","grc"],
   "preferred_username":"ivanov","name":"Иванов И. И.",
   "products":{"scanner":["operator"],"vm":["engineer"],"grc":["methodologist"]},
   "projects":["<uuid проекта>", "..."] , "iat":0,"exp":0,"jti":"<uuid>"}
  ```
  `"projects": ["*"]` — доступ ко всем проектам. Продукт проверяет подпись, `exp`, `aud` (свой id), берёт **свои** роли из `products.<id>` и при первом входе создаёт у себя теневую запись пользователя по `sub` (без пароля). Права внутри продукта по-прежнему вычисляются из ролей на каждый запрос; отзыв в платформе действует не позже TTL токена.
- Фронтенд держит access-токен в `sessionStorage` под ключом `platform.token` (общий для всех SPA на одном origin в этой вкладке); при 401 — один тихий `refresh`, затем переход на `/login?next=<текущий путь>`. Выход — `POST /api/platform/auth/logout` и очистка ключа.

**3. Проекты.** Проект (= договор на работы с заказчиком) — сущность платформы: `{id: uuid, name, client, contract_ref, period_from, period_to, status: active|archived}`. В режиме `platform` продукты хранят у себя `platform_project_id` и не позволяют создавать проекты в обход платформы; в режиме `local` — свой справочник проектов с теми же полями. Текущий проект выбирается в верхней полосе, хранится в `localStorage` ключом `platform.project` и передаётся в адресе `?project=<uuid>`, чтобы ссылки между продуктами открывали тот же проект. Связь со «Сканером»: в его `engagement` появится поле `platform_project_id`.

**4. Активы.** Источник истины об обнаруженных хостах — «Сканер». Платформа держит сводный реестр активов `{id, project_id, address, hostname, os_family, os, owner, criticality, tags[], groups[], sources[]}`, наполняемый событиями `scanner.asset.*` и ручными правками; продукты читают активы через `GET /api/platform/projects/{id}/assets` (а в режиме `local` — напрямую из «Сканера»). Ключ сопоставления актива между продуктами — `(project_id, address)`.

**5. Манифест продукта.** Каждый продукт отдаёт `GET /manifest` (без авторизации, только метаданные):
```json
{"id":"vm","title":"Устранение","subtitle":"управление уязвимостями","icon":"wrench",
 "base_path":"/vm/","api_base":"/api/vm/","version":"1.0.0",
 "roles":{"manager":"Руководитель","engineer":"Исполнитель","viewer":"Наблюдатель"},
 "nav":[{"id":"queue","label":"Очередь","path":"/vm/queue","icon":"list-checks","perm":"view"}],
 "search_url":"/api/vm/search","health_url":"/api/vm/health/ready"}
```
Оболочка строит из манифестов вкладки продуктов и меню, показывая только то, на что у пользователя есть роли.

**6. События.** Продукты публикуют доменные события через таблицу-outbox (запись в той же транзакции) и фоновую доставку `POST /api/platform/events` с подписью `X-Signature: sha256=<HMAC тела>` и повторами 1/5/15/60 мин. Конверт (в духе CloudEvents):
```json
{"id":"<uuid>","type":"scanner.run.finished","source":"scanner","time":"2026-11-04T16:54:52Z",
 "project_id":"<uuid>","subject":"run/123","data":{...}}
```
Платформа рассылает события подписчикам (продукт регистрирует свой webhook и список типов). Обработчики идемпотентны по `id`. Минимальный набор: `scanner.run.finished {run_id, status, counts}`, `scanner.asset.upserted`, `vm.ticket.created/status_changed`, `vm.remediation.verified {ticket_id, run_id, result}`, `grc.assessment.updated`, `audit.recorded`. В режиме `local` продукт может опрашивать API соседа вместо событий.

**7. Межпродуктовые ссылки и поиск.** Ссылки строятся как `/<product>/<route>?project=<uuid>` (например, со страницы находки в «Сканере» — «Открыть заявку в Устранении»). Ctrl+K в оболочке опрашивает `search_url` всех доступных продуктов и группирует результаты по продукту.

**8. Аудит.** У каждого продукта свой append-only журнал (запрет UPDATE/DELETE триггером), плюс каждая запись дублируется событием `audit.recorded` в сводный журнал платформы. Поля: время UTC, пользователь (`sub` и имя), продукт, действие, объект, проект, результат, IP.

**9. Общий UI.** Оболочка платформы поставляет npm-пакет `@platform/ui` (токены, `styles.css`, `Layout`, `ProductTabs`, `ProjectPicker`, `QuickSearch`, `ThemeToggle`, `Modal`, `Drawer`, `Pager`, `SeverityBadge`). Пока пакета нет, продукт держит у себя копию стилей «Сканера» с теми же именами классов (раздел «Единый стиль»), чтобы позже заменить её импортом пакета без переделки разметки. В режиме `platform` над боковой панелью продукта появляется строка вкладок продуктов (её рисует `Layout` при `VITE_PLATFORM=1`).

## Инженерные правила (как в «Сканере»)

- Бэкенд: Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic (миграции `0001_…`, тест-страж непрерывной цепочки), PostgreSQL 16 (SQLite только для юнит-тестов), pytest, ruff. Фоновые задачи — в процессе API на пуле потоков с записью состояния в БД и восстановлением после рестарта (без Celery/Redis на старте); выносить в отдельный воркер, когда понадобится.
- Docker Compose: `app` (API, entrypoint: проверка секретов → миграции → создание первого администратора из `.env` → запуск), `web` (nginx-unprivileged, строгий CSP, прокси `/api/*`), `db` (postgres:16, порт только на 127.0.0.1), ротация логов, healthcheck `/health/ready`. `docker compose up --build` поднимает всё одной командой. `.env.example` со всеми переменными и комментариями.
- RBAC: роли → права, проверка `require(Perm.X)` на каждом эндпоинте, разделение обязанностей (администратор не выполняет рабочих операций). Секреты (пароли, ключи SSH, токены интеграций) — шифрованием AES-GCM ключом из `.env`, никогда не возвращаются в API и не пишутся в логи и аудит.
- Список с серверной пагинацией (`limit/offset`, всего — `X-Total-Count`), индексы под фильтры.
- Каждое изменяющее действие — запись в журнал аудита.
- Документация: `README.md` (что это и как запустить), `docs/INSTALL.md` (установка, обновление, резервное копирование и восстановление), `docs/TESTING.md` (пошаговая ручная проверка на стенде с ожидаемым результатом по каждому шагу).
- CI GitHub Actions: pytest, ruff, тесты фронтенда, typecheck, lint, сборка образов.
- Работа ведётся задачами: ветка + PR на задачу, миграции нумеруются последовательно, к PR — скриншоты интерфейса в светлой и тёмной теме.
- Интерфейс и тексты — на русском; код, идентификаторы и коммиты — как удобно команде, комментарии в коде на русском.
